# 自定义主题生成器 —— 从一段描述或一张参考图生成新主题

内置主题之外还想要别的风格时走这条路：收集偏好 → 生成一套完整的区块库预览 HTML → 用户确认风格 → 转换成本 skill 的标准主题文件 → 登记进 `theme-index.md`，往后就是一套可以直接选用的内置主题。

## 什么时候走这条路

- 用户说"给我生成一套新主题""我要一个 XX 风格的排版"
- 用户上传了一张参考图，要求"照这个感觉做一套"
- 用户对现有主题都不满意，自己描述了想要的气质、配色或场景

## 第一步：收集偏好

一次问全，不要逐字段追问；用户给了参考图就用 Read 工具读图提取视觉特征。只有"主题描述"是必填项（或由参考图替代），其余缺了就按下面的规则自动补全：

| 字段 | 缺省时怎么办 |
|---|---|
| 主题名称 / 英文 ID | 按风格自动取一个（ID 见下方命名规则） |
| 主题描述 | 必填，或完全由参考图推导 |
| 参考图 | 可以没有 |
| 主题色 / 背景色 / 正文色 / 强调色 / 装饰色 | 由描述或参考图推导；背景默认白色或接近白色 |
| 字体偏好 | 按风格自动挑一个（见下方字体白名单） |
| 设计手法 / 气质标签 / 适用场景（各 2~4 个短语） | 自动生成 |
| 圆角 / 阴影偏好 | 按风格自动定 |

## 第二步：生成区块库预览

用本文末尾的生成提示词 + 收集到的偏好，产出一份完整的区块库 HTML，存到：

```
<SKILL_ROOT>/assets/theme-previews/{主题ID}.html
```

这份文件是"风格的唯一预览源"：所有区块连续排在同一页面里，用户打开浏览器一次性看完整套风格，不用逐块确认。每个区块上方可以加一行浅灰小字标出区块名方便对照（只在预览页里有，转换进正式主题库时去掉）。用户认可或要求调整之后再进第三步。

## 第三步：转换成正式主题文件并登记

用户确认风格后，把预览区块转换成 `references/theme-{标识}.md`，必须做到：

1. **补上 `<span leaf="">` 包裹**：预览生成阶段不带这个标记，转换时每个文字节点都要包一层，装饰性的空元素（分隔线、竖线之类）内部放 `<span leaf=""><br></span>`——这是粘贴到公众号不掉样式的前提，不能省。
2. **五个必备部分**（和"添加新主题的规范"一致）：设计变量速查表、各组件完整 HTML（从预览区块里精选 20~35 个核心组件，编组为组件族，预览文件本身保留全量）、完整文章模板骨架、文章类型→组件组合配方表、Markdown→组件映射规则表。
3. **平台红线复查**：去掉预览阶段用于定位的 `id="block-*"`（正式组件 HTML 不需要 id）、禁用标签、超过 24px 的字号；`<table>` 只保留真正的表格语义，不作为布局手段。
4. **登记 `theme-index.md`**：主题名 / 主色 / 适用场景 / 组件库文件 / 正文下划线 CSS（从强调色或装饰色推一条 `border-bottom` 样式）。
5. **跑校验**：`python3 scripts/component_lint.py .` 必须 0 ERROR，有就改完再交付。
6. **交付时说清楚**：主题名、ID、预览文件路径，并提醒用户以后可以直接说"用 XX 主题排版"。

## 维护

- 改已有生成主题：改 `theme-{id}.md`，同步改预览 HTML，重新跑 lint。
- 删除：删掉 `theme-{id}.md`、预览 HTML、`theme-index.md` 里对应那一行。
- 名字或 ID 撞车了：问用户要换名还是确认覆盖。

## 生成提示词（收集好偏好后，原样套用执行）

你是一个微信公众号文章排版区块库的设计生成器。任务不是写一篇文章，而是生成一整套**可复用的主题区块样例**，用于后续排版时挑选组件、预览风格。

**核心约束：骨架必须从输入推导出来，不能套用任何一套现成主题的结构再换皮**。先在心里给这套主题定一个"结构模型"，再决定要哪些区块、权重怎么分：

- 这套主题更偏内容叙事、信息说明、目录式组织，还是数据展示？
- 适合高密度多卡片强分隔，还是低密度大留白弱分隔？
- 标题体系更像刊头式、栏目条式、章节编号式、标签索引式，还是便签贴纸式？
- 媒体区、流程区、对比区、数据区、结尾区分别该用什么视觉语法？

不同倾向对应不同的区块重心，比如：偏杂志叙事的可以多给刊头、摘要、编者按、拉页图文；偏文档教程的可以多给目录、参数表、步骤条、FAQ、检查清单；偏科技系统的可以多给状态卡、指标条、终端式代码块；偏品牌故事的可以多给价值主张段、关系卡、证言、收束总结；偏生活记录的可以多给便签、拼贴图、清单卡、日程条。即使不同主题都要覆盖同一批通用语义（标题层级、正文、引用、列表、媒体、代码、数据、对比、流程、FAQ、作者信息、结尾），具体形式也要因主题而异——不能变成"同一套骨架换个配色"。

**输入信息**（部分字段可能为空）：主题名称、主题 ID、主题描述（必填）、参考图（可空）、主题色/背景色/正文色/强调色/装饰色、字体偏好、设计手法/气质标签/适用场景标签（各可空，自动生成）、圆角偏好、阴影偏好。

**命名规则**：
- 没给主题名就按整体风格自动取一个中文名；没给 ID 就自动生成一个。
- ID 必须以 `theme-` 开头，只能用小写字母、数字、连字符，12~40 字符，要能体现特征（例如 `theme-mist-glass`、`theme-stamp-ledger`）。
- 用户给了名称/ID 就直接用，缺的部分才自动补。
- 名称、ID、描述三者要互相一致，不冲突。
- 没明确要求背景色时默认白色或接近白色的浅色（如 `#FFFFFF`、`#FCFCFA`），只有描述或参考图明确要求深底、重氛围时才用深色背景。
- 命名风格可以参考别的主题怎么起名，但不能因为名字像就照搬那套结构。

**标签生成规则**：设计手法/气质标签/适用场景标签三者各聚焦不同维度（手法偏版式构图装饰手段；气质偏视觉语言和审美倾向；场景偏内容类型和行业用途），各 2~4 个中文短语、逗号分隔；用户给了就用用户的，没给才自动生成。

**字体偏好白名单**（只能从里面选一个，不在表里的值一律映射成表里最接近的）：`system` / `pingfang` / `microsoft-yahei` / `source-hans-sans` / `source-hans-serif` / `alibaba-puhuiti` / `youshe-titlehei` / `serif` / `monospace` / `kaiti` / `fangsong` / `stzhongsong` / `stfangsong` / `stkaiti` / `yuanti`。

**参考图处理规则**：有参考图时先提取主色/辅助色、背景氛围、留白比例、构图节奏、圆角/阴影强度、材质肌理、装饰元素、信息密度这些视觉特征，再把它们转译成区块库的配色/版式/卡片层级/标签/分隔线等设计语言——**只借气质，不复刻参考图里具体的文字、Logo、商标、人物或可识别的版权内容**。图和文字偏好冲突时，以用户明确写出来的文字偏好为准。

**输出格式**：

1. 文件开头先输出一段元信息注释（字段名固定，值按实际情况填）：

```
<!-- THEME-NAME: xxx -->
<!-- THEME-ID: xxx -->
<!-- THEME-DESCRIPTION: xxx -->
<!-- THEME-COLOR: xxx -->
<!-- THEME-BACKGROUND-COLOR: xxx -->
<!-- THEME-TEXT-COLOR: xxx -->
<!-- THEME-ACCENT-COLOR: xxx -->
<!-- THEME-DECORATION-COLOR: xxx -->
<!-- THEME-FONT-PREFERENCE: xxx -->
<!-- THEME-DESIGN-TECHNIQUE-TAGS: 标签1, 标签2, 标签3 -->
<!-- THEME-STYLE-FEATURE-TAGS: 标签1, 标签2, 标签3 -->
<!-- THEME-SCENE-TAGS: 标签1, 标签2, 标签3 -->
<!-- THEME-RADIUS-PREFERENCE: xxx -->
<!-- THEME-SHADOW-PREFERENCE: xxx -->
```

2. 之后是完整的区块集合。每个区块前用注释标出区块名（如 `<!-- Block: 栏目条式章节标题 -->`），紧跟一个顶层 `<section>`/`<figure>`/`<hr>`，顶层元素带一个稳定 id，命名规则是 `block-{主题ID缩写}-{语义名}`（如 `block-stone-hero-card`）。

3. 这是一整套区块库，不是一篇文章：数量建议 45~75 个，覆盖一套成熟主题该有的层次，但不要做成固定清单式罗列——按上面说的"结构模型"决定哪些类别该多给几个变体、哪些该少。至少要覆盖这些语义类别：头图/封面、章节标题/小节标题/标签标题、正文段落/强调段落/行内代码、引用/提示/警示/成功/信息卡、步骤/流程/时间线、图片/图片占位/双图对比/视频占位、代码块（深色+浅色）、表格/指标卡/进度条、列表/任务清单、FAQ/作者信息/联系方式/下载引导/延伸阅读、结尾总结/互动引导。区块命名要具体贴合这套风格本身的气质（比如同是"章节标题"，纸感复古风可以叫"票根式章节签"，科技风可以叫"终端状态条"），不要通篇都叫"标题块""卡片块"。

4. 每个区块都要填**示意性占位内容**，不能留空，也不能写成某个真实产品/真实活动/真实版面的具体内容——用"标题占位""说明文字占位""按钮文案占位""流程节点占位"这类表达，不出现具体品牌名、人名、地名、价格、日期、航班号等强真实感信息，语气可以贴合这套风格（比如杂志风用"专题导语占位"，科技风用"状态信息占位"），但始终让人一眼看出这是结构演示，不是真实业务页面。

5. 颜色体系围绕主题色/背景色/正文色/强调色/装饰色展开；没明确要深底时默认浅背景，靠边框、留白、浅色层、装饰色区分层次，不要整页铺深色。design/style/scene 三类标签要真的影响区块的版式手法、视觉气质和内容语气，圆角偏好影响 `border-radius`，阴影偏好影响 `box-shadow`（偏好是"无"就基本不用阴影）。同一套区块库里要反复出现一致的视觉语言（同样的边框/标签/分隔线/标题条风格），不要内部风格打架。

6. **微信兼容是第一优先级**，结构和样式都要服从这一点，而不是服从网页语义完整性或"现代 CSS 写法"：
   - 标签只用 `section`/`p`/`span`/`img`/`figure`/`figcaption`/`hr`/`br`/`strong`/`em`/`code`/`a`；禁止 `<style>`/`<script>`/`<div>`/表单类标签（`form`/`input`/`button`/`textarea`/`select`）/`video`/`audio`/`canvas`/`svg`/`iframe`。
   - 不用 CSS Grid、复杂多层 flex、`position:sticky/fixed`、`backdrop-filter`、CSS 变量、伪元素、媒体查询、悬停/过渡/滤镜等交互态。
   - `table` 只在真的是表格语义（参数表、对照表）时才用，不能拿来当卡片栅格、按钮排布、分栏布局的工具。
   - 不依赖 `aspect-ratio`/`object-fit`/`gap`/`z-index`/复杂绝对定位来撑起核心布局——就算用了，也不能是结构成立的前提。
   - 所有关键样式写在元素自己的 `style` 里，不依赖 class、外链样式表或全局继承；优先用 `margin`/`padding`/`color`/`background`/`font-size`/`line-height`/`font-weight`/`text-align`/`border`/`border-radius`/`display`/`width`/`height`/`max-width`/`box-sizing` 这类稳定属性。
   - 所有字号 ≤ 24px，哪怕是头图主标题、强调数字、CTA 主文案也不例外。
   - 图片用标准 `<img>`，`style="max-width:100%;height:auto;display:block;margin:0 auto;"`（不要 `width:100%` 强行铺满），配一个贴合语义的中文 `alt`；没有真实图片时，占位图用形如 `https://placehold.orence.net/宽x高?text=占位文字` 的地址（支持配色、格式、文字等参数，如 `/600x400/0f172a/e2e8f0?text=占位&font=cn`）。
   - 按钮用带样式的 `a` 或 `span` 模拟，不用真正的表单按钮；视频/图表一律降级成静态占位区块。
   - 输出前自检一遍：复制到公众号编辑器后，不依赖外部 CSS/JS 也能保住主要视觉层级；没有用到被禁止的标签或交互能力；就算部分样式退化，内容结构和阅读顺序依然完整。

7. 直接输出纯 HTML，不要解释性文字，不要包 Markdown 代码围栏。

现在请根据我提供的偏好，生成完整的区块库 HTML。
